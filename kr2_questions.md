1. Приложение в контейнере принимает соединения на адресе `127.0.0.1:<порт>`, порт опубликован как `127.0.0.1:<порт>:<порт>`. Почему обращение с сервера завершается ошибкой? Почему адрес `0.0.0.0` внутри контейнера не делает приложение доступным из сети?

**`127.0.0.1` внутри контейнера** — это loopback самого контейнера. Docker перенаправляет порт на сетевой интерфейс контейнера, а приложение слушает только loopback, поэтому соединение завершается отказом. `0.0.0.0` внутри контейнера лишь разрешает подключения ко всем интерфейсам контейнера; внешний доступ всё равно определяется публикацией порта на хосте. Для внешнего доступа нужен bind приложения на `0.0.0.0`, а публикация `127.0.0.1:8004:8004` оставляет доступ только с хоста или через локальный прокси.

2. Файл `.env` удалён из репозитория отдельным коммитом. Можно ли считать пароль из шаблона секретным? Что нужно сделать с паролем и что можно сделать с историей, учитывая, что ветка `main` уже опубликована?

Пароль из шаблона `.env.example` не является секретом: репозиторий доступен другим, а шаблон предназначен для публикации. Реальный пароль нужно считать скомпрометированным, немедленно заменить в Redis, `.env` и конфигурации развёртывания. Удаление файла новым коммитом не удаляет его из истории. Историю можно переписать с помощью `git filter-repo` и force-push, но опубликованная ветка уже могла попасть в клоны, кеши и форки. Поэтому главное действие — ротация пароля; переписывание истории является дополнительной мерой.

3. Почему секрет нельзя удалить из образа, добавив в конец `Dockerfile` инструкцию `RUN rm .env`? Чем это опасно при публикации образа в реестр?

`RUN rm .env` создаёт новый слой, но предыдущий слой с файлом остаётся в образе. Секрет можно извлечь через историю слоёв, `docker save` или из кеша сборки. При публикации в реестр старые слои могут остаться доступными. Секрет не следует копировать в образ; используйте runtime secrets, BuildKit secrets или внешний `.env`.

4. Почему `CMD` записывается в exec-форме? Как определить, какой процесс в контейнере имеет PID 1?

Exec-форма:

   ```dockerfile
   CMD ["gunicorn", "--bind", "0.0.0.0:8004", "app:app"]
   ```

   запускает Gunicorn непосредственно, без дополнительного shell-процесса. Он получает PID 1 и корректно принимает сигналы остановки. Проверить можно так:

   ```bash
   docker exec <container> ps -p 1 -o pid,ppid,user,args
   docker top <container>
   ```

5. Кто и в какой момент подставляет значения `${REDIS_PASSWORD}` и `$$REDIS_PASSWORD` в `docker-compose.yml`? Что изменится, если в проверке готовности записать `${REDIS_PASSWORD}`?

`${REDIS_PASSWORD}` подставляет Docker Compose при разборе файла — из shell, `.env` или `--env-file`. `$$REDIS_PASSWORD` Compose превращает в буквальный `$REDIS_PASSWORD`; затем `CMD-SHELL` внутри контейнера подставляет значение из переменной окружения контейнера.

   Если в healthcheck написать `${REDIS_PASSWORD}`, пароль будет подставлен на хосте при запуске Compose и попадёт в конфигурацию healthcheck. Это повышает риск утечки через `docker inspect`, логи и диагностические данные. Поэтому используется `$$`.

6. Почему команда сервиса `redis` начинается с `redis-server`, а не с `sh -c "redis-server …"`? Как проверить, от имени какого пользователя работает Redis?

Прямая команда:

   ```yaml
   command: ["redis-server", ...]
   ```

   делает Redis основным процессом контейнера, без лишнего shell, и обеспечивает корректную обработку сигналов. Проверить пользователя можно так:

   ```bash
   docker exec <container> id
   docker exec <container> ps -o pid,user,args -p 1
   ```

   Также:

   ```bash
   docker inspect -f '{{.Config.User}}' <container>
   ```

7. Порт Redis не опубликован. Зачем в таком случае пароль? Кто может обратиться к Redis?

Пароль нужен даже без публикации порта: любой контейнер в той же Docker-сети может обратиться к `redis:6379`. Это прежде всего защита от несанкционированного доступа со стороны других контейнеров или скомпрометированного приложения. Из внешней сети Redis напрямую недоступен, если порт действительно не опубликован.

8. Чем `depends_on` с условием `service_healthy` отличается от `depends_on` без условия? Что увидит пользователь в первые секунды после запуска при отсутствии условия?

`condition: service_healthy` запускает `app` только после успешного healthcheck Redis. Без условия Compose лишь запускает Redis раньше, но не ждёт его готовности. В первые секунды приложение может уже принимать запросы, но обращения к Redis будут завершаться ошибками, обычно HTTP 5xx или ошибками прокси.

9. Что произойдёт с данными после `docker compose down`, после `docker compose down -v` и после замены тега образа на `redis:latest`?

   - `docker compose down` удаляет контейнеры и сеть, но сохраняет именованный том `redis_data`; данные остаются.
   - `docker compose down -v` удаляет также именованный том; данные Redis теряются.
   - Замена образа на `redis:latest` может привести к загрузке и запуску другой версии Redis, но том обычно сохраняется. Тег `latest` нестабилен и может неожиданно изменить версию приложения.

10. Зачем для `<имя>.devops.local` выпущен отдельный сертификат? Что выведет `curl --cacert ~/devops.crt https://<имя>.devops.local` и почему? Как Nginx выбирает сертификат, если на порту 443 описано несколько блоков `server`?

Отдельный сертификат для `kv.devops.local` нужен, потому что имя должно присутствовать в `Subject Alternative Name`. Сертификат только для `devops.local` не пройдёт проверку имени.

    ```bash
    curl --cacert ~/devops.crt https://kv.devops.local
    ```

выведет тело HTTP-ответа, если имя разрешается, сертификат доверен и содержит `kv.devops.local`. Если сертификат не соответствует имени, curl завершится ошибкой проверки hostname.

Nginx выбирает сертификат по SNI, переданному клиентом: сначала ищется подходящий `server_name`, а при отсутствии совпадения используется default server (обычно первый блок или явно отмеченный `default_server`).

11. Какое значение выводится в строке `client` ответа `/whoami`? Почему приложение не может определить адрес клиента по TCP-соединению? Почему значению `X-Forwarded-For`, полученному напрямую от клиента, доверять нельзя?

В строке `client` выводится значение заголовка `X-Real-IP`. При проксировании из конфигурации Nginx это обычно реальный IP клиента, видимый Nginx:

    ```nginx
    proxy_set_header X-Real-IP $remote_addr;
    ```

TCP-соединение приложения установлено с Nginx, поэтому само приложение видит адрес прокси, а не исходного клиента. Заголовку `X-Forwarded-For`, присланному напрямую клиентом, доверять нельзя: клиент может указать в нём любой IP. Доверять ему можно только после удаления/перезаписи заголовка доверенным прокси.

12. Что произойдёт со всеми ресурсами стенда после `sudo reboot`? Какие службы и контейнеры запустятся автоматически, какие нет и почему?

После `sudo reboot`:

    - включённые службы systemd, например Docker и Nginx, запустятся автоматически;
    - существующие контейнеры с `restart: unless-stopped` обычно будут восстановлены Docker после запуска daemon;
    - тома и Docker-сети сохранятся;
    - сам `docker compose up` не выполняется автоматически, если контейнеры ранее не были созданы;
    - сборка образов заново не выполняется.

    Это зависит от того, включены ли соответствующие systemd-службы и не были ли контейнеры явно остановлены.

13. Почему запись в файле `hosts` нужна на хостовой системе и не нужна на сервере для работы обратного прокси-сервера?

Запись в `hosts` нужна на клиентском компьютере, чтобы `kv.devops.local` разрешался в IP виртуальной машины. Nginx на сервере уже получает запрос и выбирает блок `server` по SNI/заголовку `Host`; ему не нужно разрешать собственное `server_name`. Запись на сервере потребовалась бы только для исходящих запросов самого сервера к этому имени.

14. Порт приложения ошибочно опубликован как `"<порт>:<порт>"`. Почему UFW не препятствует доступу из сети? Обнаружит ли это проверка раздела `[5]` сценария аудита из ПР № 7? Какую проверку нужно добавить?

`"8004:8004"` публикует порт на всех интерфейсах хоста (`0.0.0.0`). Docker выполняет NAT до правил UFW, поэтому UFW может не препятствовать такому доступу.

    Проверка `[5]` это не обнаружит: она проверяет только порты `5000` и `5432`. Текущая проверка `[6]` для KR2 уже сравнивает результат:

    ```bash
    docker compose port app 8004
    ```

    с ожидаемым `127.0.0.1:8004`, поэтому она обнаружит ошибку. Для общей проверки в `[5]` следует добавить контроль публикации `8004` или проверять, что любой опубликованный служебный порт привязан только к `127.0.0.1`.
